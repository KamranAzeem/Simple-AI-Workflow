## CP-2026-09-09-01: Fixed checkpoint procedure never writing the daily checkpoint file

**Problem**: Procedure C mandated writing the three **Project AI State Files** but never wrote a file in **Project Daily Checkpoints Directory** — only Procedure B (bootstrap, one-time) ever created one. Meanwhile `ai-policy-common.md`'s Source-of-Truth Order and State File Proof-of-Read rule both already assumed a current checkpoint file existed. Result: state files raced ahead with new CP IDs every checkpoint while `ai/daily-checkpoints/` only advanced when an AI session happened to write one unprompted. Reported from an elmera-project session (`ai/issues/checkpoint-procedure-never-writes-daily-checkpoint-file.md`) and confirmed live in this repo: state files were already at CP-2026-09-07-02 while the latest file on disk was `2026-09-04.md`.

**Fix**: Added a new step 2, **Write Daily Checkpoint File**, to Procedure C in `AGENTS.md`, between the Atomic Write Protocol (step 1) and Log Condensation (renumbered 2→3; Update Project Knowledge 3→4; Context Re-affirmation 4→5). One internal cross-reference to the old step 2 (the horizon-shield mention) was corrected to "(Step 3)".

**Naming convention — deliberate deviation from the issue's raw proposal**: the issue's proposed fix cited an elmera-project example using `YYYY-MM-DD-NN.md` (one file per checkpoint). Investigated this repo's own `ai/daily-checkpoints/` directory instead and found the convention actually in force since 2026-06-19 is one file per **calendar day** (`YYYY-MM-DD.md`) with multiple `## CP-<ID>: <title>` sections appended for same-day checkpoints (verified via `2026-08-25.md`, which holds four checkpoint sections). Used that convention rather than importing an example from a different project that was never actually the standard here.
